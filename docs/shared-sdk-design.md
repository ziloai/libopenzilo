# Shared Rust SDK design proposal

Status: design reference with implementation in progress from the 2026-10-27 audit.
The current crate implements engine/policy, download/sink state machines,
shared calibration/profiles, audio export, distance validity and deadline budgets.
Adapters compose these objects rather than exposing the conceptual single Effect
envelope below. Optional native decoders remain unavailable; platform decoders stay
supported. See [API](api.md) and [validation](validation.md) for delivered scope.
[Chinese design](shared-sdk-design.zh-CN.md).

Rust should own device contracts, portable operation policies, state machines and
algorithms. Python and Android execute platform I/O and expose idiomatic public
interfaces. Applications across supported platforms should share the same
validation and operation behavior.

## Migration inventory

| Current owners | Portable responsibility |
|---|---|
| Python `_client.py`, Kotlin `ProtocolClient` | Admission, operation state, resource ownership, timeout recovery, event ownership |
| `_compatibility.py`, Kotlin discovery/gates | Capability negotiation, provenance, unknown states, verified legacy profiles, command contracts |
| `_recording.py`, Kotlin recording methods | Configuration/readback, lost-ACK ambiguity, terminal/saved confirmation |
| `_audio.py`, Kotlin download | Normal/quick download, gaps, bounded retransmission, completion and cleanup |
| `_live_audio.py`, existing Rust LiveValidator | Subscription lifecycle, sequence/counters, completeness and limits |
| `_ota.py`, Kotlin updateFirmware | Preflight, transfer/reboot/reconnect lifecycle, identity/version verification |
| `_imu_calibration.py`, `_imu_profiles.py` | Physical units, static windows, six-face fit, gyro bias, validation and profile schema |
| `_codec.py`, `_pcm.py` | Containers, PCM block semantics and optional decoder backends |
| Android distance adapter | Distance observations, confidence, timestamp validity, connection generation and expiry |
| `_device.py` | Log/time-sync protocol and identity rules |

These files also contain platform adapters; migrate responsibilities rather than
translate entire files. Reuse existing Rust implementations, including
LiveValidator, AudioAssembler and OtaTransfer, before introducing replacements.

## Modules

Keep one Cargo package initially. Organize modules as model, protocol, engine,
device, operations (recording/download/live/OTA/logs), sensors (IMU/calibration/
profiles), audio, finding and ffi. Sensor data processing and health analysis
can be added as Rust modules according to product needs and shared through
the same interfaces.

## Host-driven engine

The proposed DeviceEngine consumes user operations, notifications, write results,
disconnection/reconnection results and clock advancement. It emits effects to
send frames, reconnect, adjust timers, publish events or complete an operation.

Conceptual methods: start, on_notification, on_write_completed, on_disconnected,
on_transport_ready, tick, cancel and next_deadline. They are proposed APIs.
Hosts report transport readiness/limits; the engine initiates identity and
capability queries so reconnect adapters do not duplicate negotiation.

The host serializes inputs for each engine; locking alone does not define event
order. Rust owns logical operation/request/write/subscription IDs. Bindings own
Future/Task/Flow objects and their scheduling. Avoid an internal hidden async
runtime or platform I/O threads in the first core engine.

Distinguish generated bytes, completed platform writes and device acknowledgement.
Rust owns deadlines, retry budgets and recovery decisions. Hosts read monotonic
clocks and execute/acknowledge cleanup effects. Unix wall time is a separate input
for time synchronization. Cancelling does not undo a command already delivered.

The wire protocol has no transaction IDs. Local IDs cannot resolve late replies
after same-command retries. Never blindly retry non-idempotent START operations;
return recovery advice such as reconnect-and-query. Model recording as idle,
active, finalizing or unknown; reconnect and a lost ACK do not establish idle.
Track live/IMU/download/OTA resource use and enforce a shared compatibility policy.

Errors carry stable codes and structured parameters for device rejection,
contract mismatch, gaps, unknown outcomes, reconnection and phase timeouts.
Bindings preserve existing exceptions and localize diagnostics without matching
error-message strings.

## Contracts and identity

Centralize command-to-feature requirements, negotiation, provenance and verified
legacy profiles. A timeout is unknown, not proof of unsupported behavior. Cache
by connection generation/identity and renegotiate after OTA. Do not infer support
from product names or firmware prefixes.

Separate a platform locator from device identity. An Android/BlueZ address is not
a portable calibration identity. New profiles should use verified stable device
identity, plus firmware/model/ranges/raw-data checks. Without reliable identity,
keep profiles platform-local. Do not automatically reinterpret old address hashes
as cross-platform device identities. Version core, contract, build and bindings
separately; a Python source hash alone does not identify the linked Rust engine.

## Operations

Recording distinguishes ACK, capture, finalization and saved completion. Preserve
legacy readback values separately from allowed outgoing settings. Downloads share
normal/quick behavior, offsets, conflicting overlaps, bounded retries, size limits
and END confirmation; downloading never implies deletion. Live frames remain
provisional until a validated END, with explicit bounded buffering/overflow rules.

OTA shares preflight, signing/target checks, conflicting-operation shutdown,
transfer, reboot, reconnect budget and same-device/exact-version confirmation.
Hosts perform reconnects; Rust decides whether installation is confirmed.
Transfer bytes, device acknowledgement and verified running firmware are distinct.
Keep independent trust anchors, explicit test-firmware choice and deletion
confirmation; never embed production private keys.

Use bounded in-memory results for small downloads and chunk/backpressure effects
for larger data. Hosts choose storage and acknowledge accepted chunks. Rust does
not select filesystem paths or write user files.

## Algorithms

Move IMU unit conversion, continuity, static/saturation/drift checks, six-face fit,
gyro bias and independent validation. Retain the current algorithm's limits:
diagonal accelerometer calibration and gyro bias, without claiming cross-axis or
gyro-scale fitting. Distinguish raw and calibrated types to prevent double
correction. Preserve and version experimental thresholds; a port is not hardware
accuracy acceptance. Share profile schema/checks; hosts own files and UI guidance.

Unify audio container parsing/writing, PCM units/channels/sample offsets and stream
semantics first. Optional Rust-owned backends may wrap established Opus/Speex
implementations; rewriting codecs is unnecessary. FFmpeg/PyAV can remain optional
host backends. Playback/device routing stays platform-specific. Keep the FFI
surface stable, expose library_features, and return typed Unavailable errors when
a backend is not compiled in so bindings cannot silently mismatch native variants.

Finding is distance-only. Android acquires standard BLE CS measurements using
RangingManager. Rust normalizes units, quality, timestamps and connection
generations, with waiting/measuring/low-quality/stale/unavailable/disconnected
states. Preserve the platform's confidence semantics without presenting it as a
calibrated probability. Reject invalid, old-connection and stale measurements;
clear expired readings. Hosts convert system timestamps to the agreed monotonic
clock domain and manage permissions, pairing, sessions, display and localization.

The first version preserves valid raw distances without unvalidated smoothing or
extrapolation. Python can replay identical distance observations for policy tests;
live CS availability remains platform/hardware-dependent. Camera tracking, pose
fusion, multilateration, bearing and spatial positioning are outside the scope.

## Platform boundary

Python retains Bleak, asyncio objects, CLI/confirmation, paths/storage, playback and
optional external decoders. Android retains BluetoothGatt/pairing/permissions,
coroutines/Futures/Flow, lifecycle/background policy, storage, system ranging,
audio output and UI. Platform adapters implement MTU fragmentation
and write acknowledgements without interleaving protocol frames. Rust owns logical
frame ordering. Batch samples, audio blocks and events across FFI.

## Order and acceptance

1. P0: common errors, capability policy, operation/resource engine and full
   recording/download/live/OTA lifecycles. Preserve Python API/exception adapters.
2. P1: IMU algorithms and portable profile validation/migration.
3. P1: distance observation, quality/expiry policies and Python distance replay.
4. P2: audio containers/stream semantics, then optional validated decoder backends.

Use identical synthetic/de-identified inputs across Rust/Python/Android and compare
results, error codes and state transitions. Remove replaced platform business
implementations. Keep public API regressions and hardware checks, with pure tests
independent of BLE and platform tests for writes/cancellation/reconnection/cleanup.
Keep each migration buildable; decide on separate optional crates after the first
unified engine is accepted.
